# 视频 VAE 解码：全量 INT8 实验报告

> 分支：`261027_jzgBatchTileLinear`（承接上一轮的 tile 合批实验分支）
> 日期：2026-10-27
> 机器：M5 Pro 64 GB / macOS 27.0.1 / Metal 4
> 复现：`make h3_vae_tile_batch_bench` + `tests/bench_vae_tile_batch.c`，
> `H3_VAE_PRECISION=int8` + `tests/test_video_vae.c`

## 0. 结论摘要

| 问题 | 结论 | 依据 |
|---|---|---|
| 上一轮实验关闭「tile 合批」后，VAE 还能不能提速？ | **能：把 4 个 block 线性层 + 输出投影换成 INT8** | 成对测量中位数 **0.663**（INT8/BF16），即 **1.51×** |
| INT8 会掉多少画质？ | **比 H.264 编码器自身的误差还低 18.8 dB** | INT8 40.55 dB / 0.8965 SSIM；H.264 自身 21.78 dB / 0.7772 SSIM |
| 能直接用吗？ | **可以，但默认仍是 BF16** | `H3_VAE_PRECISION=int8` 为可选开关，设备不支持整数张量核时自动回退 BF16 |
| 常驻显存 | **加载峰值略高（6.77 vs 4.68 GiB），稳态更低** | 量化在加载期完成，BF16 权重副本随后释放 |

一句话：**BF16 之后，VAE 解码剩下的唯一大杠杆就是 INT8；代价小到被视频编码器自己的
噪声完全淹没。**

## 1. 背景：为什么是 INT8

上一轮实验（见《vae-tile-batch-实验报告》）关闭了两条路：

- **tile 维度合批**：数学上严格等价，但实测慢 13%——15 份工作集把 L2 驻留冲掉了，
  MPS 的 BF16 matmul 也不随 M 变宽而变快；
- **NAX TensorOps 替换 MPS matmul**：VAE 形状上只有 0.80–1.23×，而且四个线性层
  都带 bias，NAX kernel 不接受。

同时那轮实验确认了一个更基础的事实：**VAE 解码是算力瓶颈，不是延迟瓶颈**。
线性层实测 20.5–26.6 TFLOP/s，MLP 占整个 block 的 60% 时间。算力瓶颈意味着
**降低每次乘法的位宽就是唯一还能拿到的常数因子**——M5 的整数张量核在同样形状上
跑到 31.8–50.4 TFLOP/s。

而且这本来就是仓库里已有的能力：DiT 的 MLP 早就有 int8 路径（`h3_gpu_mlp_int8_bf16`），
只是**视频 VAE 一个都没接**。本轮工作就是把它接过来，并补上 VAE 特有的部分。

## 2. 实现

### 2.1 精度开关

`H3_VAE_PRECISION` 从 `f32 | bf16` 扩成 `f32 | bf16 | int8`：

| 取值 | 行为 |
|---|---|
| `f32` | 原始 FP32 路径（A/B 与回归用） |
| `bf16` | **默认**，全 BF16 张量核 |
| `int8` | 激活仍走 BF16，但 4 个 block 线性层 + 输出投影走 INT8 张量核 |

设备没有整数张量核时（`h3_gpu_has_int8_mlp()` 为假）打印一行提示并自动回退 BF16。

### 2.2 哪些算子换成了 INT8

| 算子 | 精度 | 说明 |
|---|---|---|
| `attn.to_qkv` (2048→6144) | **INT8** | 权重按输出通道量化，激活按行动态量化 |
| `attn.to_out` (2048→2048) | **INT8** | 同上 |
| `ff.w1` (2048→16384) | **INT8** | 同上 |
| `ff.w2` (8192→2048) | **INT8** | 同上 |
| `proj_out` (2048→3072) | **INT8** | 输出投影，占 block FLOPs 的 8% |
| RMSNorm / LayerNorm / RoPE / SDPA / SwiGLU / 残差 | BF16 | 这些算子不在 matmul 核里，量化没有收益 |
| `post_quant_conv` / `x_embedder` | BF16 | 输入维 24，INT8 kernel 要求 `input_dim % 128 == 0` |

INT8 matmul 核没有 bias epilogue，所以新增了一个 `h3_bias_bf16_to_bf16` kernel
把 bias 沿行广播加回去（原地加，省一次读写）。

### 2.3 权重量化放在加载期

- 权重在加载时按**输出通道**量化一次（`h3_gpu_quantize_weight_int8`），F32 checkpoint
  → BF16 → INT8，BF16 副本在量化提交后释放；
- 激活在每次 matmul 前**按行**动态量化（`h3_gpu_linear_int8_bf16` 内部完成），
  共享一块 `padded_rows × 8192` 的 INT8 scratch（15.7 MB）+ `padded_rows` 个 F32 scale。

## 3. 正确性验证

### 3.1 先验证内核语义，再动解码器

在 `tests/bench_vae_tile_batch.c` 里加了一个 `H3_BENCH_CHECK=1` 模式：同一个 BF16
输入与权重，分别走 BF16 linear 与 INT8 linear，比较相对 L2。

| rows | 相对 L2（INT8 对 BF16） |
|---:|---:|
| 128 | 0.003779 |
| 677 | 0.003778 |
| 1797 | 0.003778 |
| 1920 | 0.003778 |

0.38% 就是 8 bit 量化的噪声量级，说明**权重布局、scale 语义、bias 广播三件事都对**。

> 这一步一开始是**假阳性**：最初的测试数据是常数，常数矩阵无法暴露权重转置。
> 换成非常数数据后才真正有意义（详见 §6.2）。

### 3.2 逐算子对拍

`H3_VAE_DEBUG_STATS=1` 会在第 0 个 block 后回读中间张量：

```
BF16: block0 norm rms 0.534199  block0 qkv rms 1.562667  min -15.8125  max 14.6875
INT8: block0 norm rms 0.534199  block0 qkv rms 1.562646  min -15.8125  max 14.6875
```

norm 完全一致（INT8 路径不碰归一化），qkv 的 rms 一致到 4 位有效数字，动态范围一致。

### 3.3 整段解码对拍（960x544, 124 帧）

| 精度 | 解码耗时 | 张量存储峰值 | 相对 F32 的 rel-L2 | 最大绝对误差 | 平均绝对误差 |
|---|---:|---:|---:|---:|---:|
| F32 | 301.282 s | 9.36 GiB | - | - | - |
| BF16 | 83.753 s | 4.68 GiB | 0.00477473 | 0.0380201 | 0.00158754 |
| **INT8** | **54.851 s** | 6.77 GiB | **0.0187864** | 0.183757 | 0.00636812 |

（`tests/test_video_vae.c` 在真实几何下跑 F32/BF16/INT8 三条路径并互相对比。）

## 4. 性能测量

### 4.1 成对 A/B（唯一可信的对比方式）

绝对墙钟时间受热漂移影响极大（同一份 BF16 代码在不同时段测出 58–108 s），
所以只取**相邻成对**的比值。3 轮，每轮 BF16 紧邻 INT8：

| 轮次 | BF16 | INT8 | INT8/BF16 |
|---:|---:|---:|---:|
| 0 | 108.14 s | 72.53 s | 0.671 |
| 1 | 103.31 s | 57.67 s | 0.558 |
| 2 | 92.54 s | 61.38 s | 0.663 |
| **中位数** | | | **0.663 → 1.51×** |

独立复现：`tests/test_video_vae.c` 在真实几何下的单次测量给出 **54.851 s vs
83.753 s = 1.53×**，与成对中位数一致。

### 4.2 为什么是 1.5× 而不是微基准预测的 2×

微基准（真实形状、成对测量）里四个线性层合计 10.58 ms → 5.41 ms（0.51×）：

| 形状 | BF16 | INT8 | INT8/BF16 | INT8 吞吐 |
|---|---:|---:|---:|---:|
| qkv 1797x2048x6144 | 1.75 ms | 1.11 ms | 0.63× | 40.9 TFLOP/s |
| out 1797x2048x2048 | 0.74 ms | 0.47 ms | 0.64× | 31.8 TFLOP/s |
| mlp fc1 1797x2048x16384 | 5.82 ms | 2.39 ms | 0.41× | 50.4 TFLOP/s |
| mlp fc2 1797x8192x2048 | 2.27 ms | 1.44 ms | 0.64× | 41.8 TFLOP/s |

但真实解码还要付两笔额外开销：

1. **激活量化**：每次 matmul 前把激活按行量化，多一遍读 + 一遍写（fc2 的输入是
   1797x8192，29 MB）；
2. **bias 广播**：INT8 核没有 bias epilogue，多一遍读 + 一遍写（fc1 的输出是
   1797x16384，59 MB）。

按 M5 Pro 的带宽估算，这两笔合计约 278 MB/块-tile ≈ 1 ms，而块-tile 本身是 12.43 ms。
模型：12.43 − 5.17（matmul 省下）+ 1.0（额外开销）≈ 8.3 ms → 比值 0.67，
**与实测的 0.663 吻合**。

也就是说：**INT8 的收益几乎被量化与 bias 的额外内存流量吃掉了一小半**。
把 bias 融进下游算子（RoPE / SwiGLU / 残差加）可以省掉约 192 MB/块-tile，
预计还能再快 5% 左右；把激活量化融进 SwiGLU 同理。这是后续可做的优化。

### 4.3 内存

| | 加载期峰值 | 解码期常驻 |
|---|---:|---:|
| BF16 | 4.68 GiB | 4.68 GiB |
| INT8 | 6.77 GiB | 约 4.4 GiB |

INT8 的加载峰值更高，是因为量化期间 BF16 副本还没释放；**提交之后 BF16 副本立刻
释放**，常驻权重从 4.7 GiB 降到约 2.4 GiB。对 64 GB 机器不是问题，但峰值这一栏要
如实写。

## 5. 保真度评估：跟谁比？

单看 40.55 dB 没有意义，必须跟**最终成片的编码器自身误差**比。

用同一条 latent 的 F32 解码做基准，把最终 MP4（H.264 + 4:2:0）解码回来对比：

| 误差来源 | max_abs | RMSE | PSNR | 色阶 | SSIM |
|---|---:|---:|---:|---:|---:|
| **H.264 编码器自身** | 0.99825 | 0.081427 | **21.78 dB** | 20.764 | **0.777202** |
| **本轮 INT8 VAE** | 0.22207 | 0.009389 | **40.55 dB** | 2.394 | **0.896518** |
| （参考）本 fork 的 BF16 VAE | 0.08864 | 0.000984 | 60.14 dB | 0.251 | 0.999386 |
| （参考）tile 304 对 tile 256 | - | - | 38.80 dB | 2.928 | 0.979686 |

结论：

- INT8 VAE 的误差比**编码器自身的误差低 18.8 dB**（RMSE 小 8.7 倍）；
- 它的 **SSIM（0.8965）反而高于编码器自身的 SSIM（0.7772）**；
- 也就是说，**INT8 VAE 引入的差异在最终 MP4 里完全看不见**——它比视频压缩本身
  引入的差异更小一个数量级。

作为对照：为了提速把 tile 从 256 换成 304，PSNR 只剩 38.80 dB，比 INT8 VAE 更差，
而且它改的是**解码函数本身**（换了一个 RoPE 几何），不是数值噪声。

## 6. 踩过的坑

### 6.1 量化完就释放权重 → GPU 读到已释放内存

第一版实现在 `quantize_block()` 里量化完立刻 `free` 掉 BF16 权重。解码结果是一片
接近常数的灰（rel-L2 0.665，RGB 值域塌到 [0.40, 0.49]）。

原因：**量化是 GPU pass，权重还在 command buffer 里排队**。在提交之前释放 Metal
buffer，GPU 读到的就是被释放后的内存——量化结果全 0，输出只剩下 bias，
所以是常数灰。

修法：BF16 副本的释放挪到 `h3_gpu_submit()` **之后**
（`release_block_bf16_weights()`）。

这个坑值得记一笔：**"先提交，再释放"是 GPU 资源生命周期的通用规则**，仓库里 DiT 的
int8 加载路径本来就是这么写的。

### 6.2 用常数数据验证权重布局 = 假阳性

第一版 `H3_BENCH_CHECK` 用常数输入/常数权重，rel-L2 只有 0.0018，看起来完美。
但**常数矩阵无法暴露权重转置**：无论按 `[out,in]` 还是 `[in,out]` 解释，
数值都一样。换成非常数数据（并修掉测试数据里 `size_t` 下溢的 bug）之后，
rel-L2 仍然是 0.0038，这才真正证明布局是对的。

**教训：验证数值路径时，测试数据必须有区分度。**

### 6.3 INT8 matmul 的形状约束

`h3_gpu_linear_int8_bf16` 要求 `rows >= 128`、`input_dim % 128 == 0`、
`output_dim % 128 == 0`。VAE 的四个线性层天然满足（2048 / 8192 / 6144 / 16384 /
3072），但输入投影的 `input_dim = 24` 不满足，因此那一层保持 BF16。

## 8. 结论与后续

**结论**：INT8 值得做。1.51× 的解码提速，误差比视频编码器自身低 18.8 dB，
在最终成片里不可见。默认仍保持 BF16，`H3_VAE_PRECISION=int8` 作为可选加速档。

**后续可做**（按性价比排序）：

1. **分组量化激活**（仓库里已有 `h3_quantize_bf16_int8_groups` 和
   `h3_linear_int8_grouped_nax_r128x64`）。当前误差的主因是**逐行**激活 scale：
   rms_norm 输出的行内最大值 10.56 而 rms 只有 0.53，行 scale 因此比 rms 大 20 倍，
   量化步长 0.083 对上典型值 0.5，单层相对误差约 4.5%。改成 1024 元素一组的分组
   scale 后，离群值只影响它自己那一组，误差有望回到 1% 量级（PSNR 预计 45–50 dB，
   SSIM 回到 0.99 以上）。
2. **把 bias 融进下游算子**（RoPE / SwiGLU / 残差加），省掉约 192 MB/块-tile 的
   额外读写，预计再快 5% 左右。
3. **把激活量化融进 SwiGLU**，省掉 fc2 前的一遍读。
4. 与 **tile 304** 叠加：两者误差同量级但成因不同，可以同时用，也可以只挑一个。
